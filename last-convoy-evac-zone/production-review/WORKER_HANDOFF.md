# Work 전달문 — LCEZ 체크포인트 제출과 리뷰 반영

## 임무

LAST CONVOY: EVAC ZONE을 출시 가능한 게임으로 발전시키는 구현 담당은 아래 규칙을 작업 지침에 반영한다. 이 문서를 작성하거나 GitHub에 올린 것만으로 로컬 실행기·모델·예약이 설정되는 것은 아니다. 요청 모델을 실제 선택할 수 없는 환경이면 그 사실을 기록하고 임의 대체하지 않는다.

요청 배정: GPT-6 High = 설계·기술 검수, GPT-5.6 Luna Extra High = 주 구현. ChatGPT = 제작 방향 총괄 및 구현 세션과 분리된 외부 검수. 실제 모델/추론 수준은 실행 환경에서 확인 가능한 값만 기록한다. 이 문서에 모델 API 식별자나 인증키를 임의 생성하지 않는다.

## 0. 실행 전 확인

1. 사용자가 승인한 Unity 프로젝트 경로와 원격 저장소를 확인한다. 현재 확인된 portfolio-pages는 웹 참조이며 Unity 원본 업로드 대상이 아니다.
2. 기존 씬·프리팹·아트·.meta·패키지와 미커밋 변경을 보존한다. 빈 프로젝트로 덮어쓰거나 origin을 임의 변경하지 않는다.
3. production 저장소가 미확정이면 `BLOCKED: production repository not registered`를 기록한다. 관련 없는 저장소를 임의 대체하지 않는다.
4. 지정된 Unity 6.6의 실제 설치 버전과 실행 환경을 확인한다. 문서/버전 파일만 바꾼 것은 설치·전환·검증 완료가 아니다.
5. 승인된 저장소에서 작업 브랜치 `work/LCEZ-<ID>-<slug>`를 사용한다. main에 직접 푸시하거나 force push하지 않는다. 보안/브랜치 정책과 실제 권한을 우회하지 않는다.

## 1. 작업 시작

새 작업은 직전 체크포인트와 외부 리뷰부터 읽는다. 변경 없는 파일 전체를 반복 수집하지 않는다. 한 작업에는 목표, 완료 기준, 수정 가능 범위, 위험, 검증 방법, 다음 행동을 적는다.

같은 씬/프리팹/공통 설정에 동시 쓰기 작업자를 두지 않는다. 경계가 분리된 독립 과제만 별도 브랜치에서 병렬 진행한다. 실패 원인이 설계에 있으면 설계자에게 돌려보내고 테스트를 약화해서 통과시키지 않는다.

## 2. 체크포인트 커밋·푸시

다음 중 먼저 발생하는 시점에 원격 체크포인트를 갱신한다: 검증 가능한 기능 단위 완료, 실제 작업 60분 경과, 동일 실패 2회, 작업 종료·중단.

- 변경 파일 목록과 diff를 확인한다. 사용자/다른 작업자의 변경을 임의로 포함하거나 되돌리지 않는다.
- 관련된 최소 테스트를 실행한다. 환경상 실행할 수 없으면 NOT_RUN과 이유를 명시한다. 실패는 FAILED로 기록한다.
- 변경 파일을 명시적으로 선택해 스테이징한다. 검토 없이 저장소 전체를 `git add -A` 하지 않는다.
- 코드·설정 커밋을 만든 다음 그 SHA를 증거의 `tested_source_sha`로 사용한다. 증거 문서를 별도 커밋으로 추가해도 된다. 새 문서의 자기 자신의 커밋 SHA를 미리 적으려고 하지 않는다.
- 승인된 원격/작업 브랜치에만 푸시한다. 원격의 실제 HEAD SHA를 확인한다. 로컬 커밋만 만든 상태와 원격 푸시 완료를 구분한다.
- 진행 중 코드는 WIP 초안 PR로, 차단은 BLOCKED로, 완료 기준을 만족한 제출만 READY_FOR_REVIEW로 표시한다.
- 커밋 예: `checkpoint(LCEZ-012): convoy path WIP`; `feat(LCEZ-012): road-following evacuation route`; `fix(LCEZ-012): reject destroyed convoy escape`.

푸시 권한/연결/비밀정보 문제가 있으면 숨기지 않는다. 안전한 파일만 보존하고 BLOCKED 기록을 남긴다. 유료 자원 구매, 새 클라우드 서버, 저장소 공개 전환, 릴리스 배포는 별도 사용자 승인 없이 진행하지 않는다.

## 3. 제출 위치와 내용

전용 Unity 저장소에 통합할 때 권장 경로는 `docs/production/checkpoints/<WORK-ID>.md` 및 관련 PR이다. 원래 저장소의 지침과 경로가 있으면 충돌 없이 합의해 사용한다.

체크포인트에는 작업 ID, base/source SHA, PR, 상태, 정확한 Unity 버전, 실제 변경, 실행한 테스트와 개수/로그, NOT_RUN 항목, 다음 행동을 적는다. 상세 형식은 CHECKPOINT_TEMPLATE.md를 사용한다.

플레이/시각 변경에는 원본 실행 화면과 짧은 녹화, 마일스톤에는 성공·실패 경로와 통합 플레이 영상을 제공한다. 이미지 생성 결과나 설계 그림을 실제 플레이 화면으로 제출하지 않는다. 영상/빌드가 다른 SHA이면 차이를 적고 해당 변경의 검증에 사용하지 않는다.

빌드와 큰 녹화는 허용된 비공개 아티팩트 저장소를 사용하고, PR에 접근 가능한 링크·빌드 식별자·원본 SHA·필요한 만료 정보를 남긴다. 사용 중인 서비스가 실제로 제공하는 링크만 기록한다. 외부 리뷰어가 읽을 수 없는 로컬 절대경로는 제출 완료가 아니다.

공개 GitHub에는 Unity 라이선스 파일, 인증키, 계정 토큰, 개인 경로/정보가 담긴 원본 로그, 재배포 권리가 없는 유료 원본 에셋을 업로드하지 않는다. `Library`, `Temp`, 로컬 캐시와 대용량 실행 파일을 검토 없이 Git에 넣지 않는다. .meta와 필요한 프로젝트 설정은 보존한다.

## 4. 리뷰 확인과 수정

구현자는 작업 시작·체크포인트 직후·다음 작업 착수 전에 해당 PR의 `LCEZ EXTERNAL REVIEW`와 설계 리뷰를 확인한다. 리뷰가 없는 동안 무한 대기하지 않는다. 현재 모듈의 테스트/정리 또는 의존하지 않는 승인된 작업만 진행한다.

- P0/P1: 관련 기능 확대와 병합을 멈추고 원인 수정 및 회귀 테스트를 우선한다.
- P2: 대응 시점과 마일스톤 기준을 기록한다. 핵심 조작감·가독성 문제를 단순 장식 문제로 무기한 미루지 않는다.
- P3: 후속 폴리싱 항목으로 기록하되 범위를 무제한 늘리지 않는다.

각 지적에 `수정 커밋 / 재현 테스트 / 결과`로 답변한다. 이견이 있으면 재현 조건과 근거를 남긴다. 결론을 얻으려고 같은 요청을 다른 모델에 계속 반복하지 않는다.

리뷰어는 자동 병합하지 않는다. PASS는 해당 SHA와 검토 범위에 대한 의견이며 사용자 출시 승인이나 별도 인간의 승인을 대신하지 않는다. 리뷰 후 코드/설정이 바뀌면 영향 범위를 재검증한다.

## 5. 안정적인 재개

동일 오류 2회, 연속 수용량/인증 실패 등 진전 없는 상황에서는 멈추고 checkpoint에 실패 명령, 원인 가설, 다음 시도 1개, 필요한 권한을 남긴다. 비밀정보를 제외한 최소 로그만 보존한다. 작업 재개 시 마지막 원격 SHA와 로컬 변경부터 비교하며 전체 프로젝트를 처음부터 다시 만들지 않는다.

## 6. 장기 목표

목표는 도심·시골·농장 구조작전과 3D 픽셀풍 아트를 가진 Windows 싱글플레이 게임이다. 먼저 도심 한 구역의 전투·농성지·쉘터·탑승·호송·탈출·결과를 완결한다. 기존 웹 데모의 기능 명칭이 아니라 실제 성공/실패 판정과 플레이 체감을 기준으로 옮긴다. README의 M0~M6 검수 순서를 따른다.
